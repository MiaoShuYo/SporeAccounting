# SporeAccounting Android 客户端需求规格说明书

> 文档类型：迭代式产品需求文档（PRD / SRS）  
> 目标项目：`SporeAccountingAndroid`  
> 接口依据：《SporeAccounting 安卓客户端接口文档》  
> 版本：v1.0  
> 更新时间：2026-08-29

## 1. 项目概述

### 1.1 项目目标

建设一款面向个人及家庭用户的 Android 记账客户端，通过 SporeAccounting API Gateway 完成身份认证、账本管理、日常记账、预算控制、财务分析、分摊支出、文件识别和智能分类等功能。

客户端应优先保证“登录—创建账本—配置基础数据—完成记账—查看统计”主链路稳定，再按迭代增加预算、通知、OCR、智能分析和协作能力。

### 1.2 目标用户

- 需要记录个人日常收支的普通用户。
- 需要管理多个账本的用户。
- 需要与家庭成员或朋友共享账本、分摊费用的用户。
- 希望使用预算和财务健康评分改善消费习惯的用户。

### 1.3 核心价值

- 快速完成一笔收支记录。
- 清晰查看账本余额、收入和支出。
- 通过预算与报表了解消费状况。
- 通过 OCR、文本提取和分类预测降低录入成本。
- 通过共享账本和分摊支出支持多人协作。

### 1.4 当前不在范围内

- iOS、Web 和桌面客户端。
- 离线状态下的完整记账与复杂冲突合并。
- 银行卡自动同步、支付平台自动导入。
- 在 APK 中保存 OAuth 客户端密钥或调用仅供服务端使用的客户端凭证模式。
- 绕过 API Gateway 直连微服务。
- 在后端路由修复前上线周期性支出功能。

## 2. 产品与技术约束

### 2.1 客户端基线

- 开发语言：Kotlin。
- UI：Jetpack Compose + Material 3。
- 架构：单 Activity、Navigation Compose、MVVM 或 MVI。
- 异步：Kotlin Coroutines + Flow。
- 网络：Retrofit + OkHttp。
- JSON：Gson、Moshi 或 Kotlin Serialization，项目内必须统一。
- 本地存储：DataStore；需要结构化缓存时使用 Room。
- 依赖注入：Hilt。
- 图片加载：Coil。
- 最低 Android 版本：由项目初始化时确定，建议 API 26 及以上。

### 2.2 网络约束

- 所有业务请求必须通过 API Gateway。
- Base URL 必须由 `BuildConfig` 区分开发、测试和生产环境。
- 正式环境只允许 HTTPS。
- 除匿名接口外，请求携带 `Authorization: Bearer <access_token>`。
- 客户端不得伪造 `X-User-*` 和 `X-Gateway-Signature` 请求头。
- 金额优先使用 `BigDecimal`，禁止直接使用二进制浮点数参与金额汇总。
- DateTime 使用 ISO 8601；客户端内部需明确 UTC 与本地时区转换策略。
- 服务端枚举当前按整数传输，客户端必须提供显式数值映射和未知值兜底。

### 2.3 通用交互要求

每个数据页面至少具备以下状态：

- 首次加载。
- 加载成功且有数据。
- 加载成功但无数据。
- 加载失败并可重试。
- 下拉刷新。
- 分页加载中、分页失败、没有更多数据。
- 提交中，防止重复点击。

 destructive 操作必须二次确认；创建或更新成功后应给出明确反馈，并刷新相关列表或局部状态。

### 2.4 通用错误处理

- `400`：展示可理解的输入错误，保留用户已填写内容。
- `401`：单飞刷新令牌；刷新失败时清除会话并跳转登录页。
- `403`：提示无权限，不自动重试。
- `404`：展示资源不存在；若为未发布路由，记录诊断信息。
- `502/503/504`：提示服务暂不可用，提供重试入口。
- 网络断开：展示离线状态，不丢失尚未提交的表单。
- HTTP 200 + 空 body：按 `Unit` 处理。
- HTTP 200 + `null`：按业务空状态处理，不作为解析错误。

| 迭代 | 主题 | 主要交付 | 前置依赖 |
| --- | --- | --- | --- |
| Iteration 0 | 工程与联调基线 | 工程骨架、网络层、会话管理、CI | Gateway 可访问 |
| Iteration 1 | 登录与应用框架 | 密码登录、验证码、主页框架 | 测试账号、匿名路径配置正确 |

## 4. Iteration 0：工程与联调基线

### 4.1 迭代目标

建立可持续开发、测试和发布的 Android 工程，使后续功能只需关注业务模块。

### 4.2 功能需求

#### R0-01 工程初始化

- 建立 Android Kotlin + Compose 项目。
- 配置应用 ID、版本号、开发/测试/生产 Build Variant。
- 配置统一主题、颜色、字体、间距和常用组件。
- 建立 `core-network`、`core-model`、`core-ui`、`feature-*` 等模块或等价分层。

#### R0-02 网络基础设施

- 配置 Retrofit、OkHttp 和 JSON 转换器。
- 通过 `BuildConfig.API_BASE_URL` 注入环境地址。
- 实现 Bearer Token 拦截器。
- 实现统一成功、空响应和错误响应解析。
- 网络超时需大于网关 30 秒下游超时，建议读取超时 35 秒。
- Debug 构建允许安全的 HTTP 日志；日志必须脱敏 Token、密码、Cookie 和文件预签名 URL。

#### R0-03 会话管理

- 使用 DataStore 保存 access token、refresh token、过期时间和必要的用户标识。
- 实现并发安全的 Token 刷新机制。
- 刷新失败后原子清理会话，避免循环 401。
- 应用启动时根据本地会话进入登录页或主界面。

#### R0-04 通用页面状态

- 实现 Loading、Empty、Error、Content 四类基础状态组件。
- 实现通用错误提示、重试、Snackbar 和确认对话框。
- 实现分页容器或统一 Paging 方案。

#### R0-05 质量基线

- 配置代码格式化、静态检查和单元测试。
- CI 至少执行 Debug 构建、Lint 和单元测试。
- 为网络 DTO 解析、错误映射和 Token 刷新编写测试。

### 4.3 验收标准

- 可在模拟器启动并切换开发/测试 Base URL。
- 能调用网关健康接口并展示结果。
- 模拟 401 时只能发起一次刷新请求，其他请求等待同一刷新结果。
- 空 body、JSON 字符串、对象、数组、分页和错误对象均能正确解析。
- 日志中不出现完整 Token、密码或客户端密钥。

### 4.4 退出条件

- Gateway 测试环境可用。
- CI 通过。
- 网络层和会话层代码评审完成。

## 5. Iteration 1：登录与应用框架

### 5.1 迭代目标

用户能够使用已有账号进入应用，完成稳定的登录会话，并看到主导航框架。

### 5.2 功能需求

#### R1-01 密码登录

- 提供用户名、密码输入和登录按钮。
- 密码默认隐藏，可切换显示。
- 前端校验必填、长度和空白字符。
- 使用 `application/x-www-form-urlencoded` 调用 `POST /api/auth/token`。
- scope 使用 `api offline_access`。
- 登录成功保存令牌并进入主页。
- 登录失败显示服务端可用错误或通用错误，不清空用户名。

#### R1-02 图片验证码

- 调用 `GET /api/captcha/create` 获取验证码图片、Token 和有效期。
- 支持刷新验证码。
- 调用 `POST /api/captcha/verify` 校验。
- Base64 图片解析失败时展示重试入口。
- 是否将验证码接入登录流程由产品规则决定；首期至少完成独立组件和接口联调。

#### R1-03 主界面框架

- 底部导航至少预留：首页、记账、预算、我的。
- 支持登录态失效后统一跳转登录页。
- 主页展示账本入口、快速记账入口和功能占位状态。

#### R1-04 当前用户状态

- 调用 `/api/users/phone/verify` 和 `/api/users/email/verify` 获取绑定状态。
- “我的”页面展示登录状态与绑定状态。
- 后端 `userinfo` 尚未发布到网关，首期不依赖该接口获取用户资料。

### 5.3 接口范围

- `POST /api/auth/token`
- `GET /api/captcha/create`
- `POST /api/captcha/verify`
- `GET /api/users/phone/verify`
- `GET /api/users/email/verify`

### 5.4 验收标准

- 正确账号能登录并在重启应用后保持会话。
- 错误密码、无网络、服务不可用均有不同的可理解反馈。
- access token 过期后可自动刷新；refresh token 无效时返回登录页。
- 不在任何日志或 UI 中显示完整 Token。
- 图片验证码可显示、刷新和验证。

### 5.5 已知限制

注册、验证码登录、重置密码、绑定邮箱/手机号和登出接口尚未发布到网关，不纳入本迭代。

## 6. Iteration 2：账本与基础资料

### 6.1 迭代目标

用户能够管理账本，并准备记账所需的分类、币种和支付方式数据。

### 6.2 功能需求

#### R2-01 账本列表

- 分页展示账本名称、备注、收入、支出和当前权限。
- 支持下拉刷新和加载更多。
- 无账本时引导创建第一个账本。
- 记住用户最后选择的账本 ID。

#### R2-02 创建与编辑账本

- 创建字段：名称、备注。
- 编辑时 body `id` 必须与 path `id` 一致。
- 名称为空时禁止提交。
- 成功后刷新列表并定位到更新项。

#### R2-03 删除与合并账本

- 删除前展示二次确认和影响说明。
- 删除接口成功响应为空，不按 boolean 解析。
- 合并时选择一个目标账本和至少一个源账本。
- 禁止目标账本同时出现在源账本列表。
- 合并完成后刷新账本和当前选择。

#### R2-04 收支分类

- 按父分类查询子分类。
- 支持新增、重命名、调整父分类和批量删除。
- 收入类型值为 `0`，支出类型值为 `1`。
- 删除前检查 UI 中是否存在使用中的选择，并提示影响。

#### R2-05 币种与汇率

- 展示币种名称和缩写。
- 支持查询两个币种今日汇率。
- 支持查看历史汇率分页列表。
- 币种列表应缓存，允许离线读取最近一次成功数据。

#### R2-06 支付方式

- 展示支付方式、类型、电子支付子类型、默认状态和备注。
- 支持新增、编辑、删除和设为默认。
- 设置新默认支付方式后，客户端本地列表只能保留一个默认项。

### 6.3 接口范围

- `/api/account-books...`
- `/api/transaction-categories...`
- `/api/currencies`
- `/api/exchange-rates...`
- `/api/payment-methods...`

### 6.4 验收标准

- 用户可以完成账本 CRUD 和合并。
- 所有枚举显示为中文文案，不直接显示整数。
- 可配置完整的记账基础数据。
- 空响应接口不会触发 JSON 解析错误。
- 账本权限为只读时，客户端隐藏或禁用编辑入口；服务端 403 仍能正确处理。

## 7. Iteration 3：核心记账闭环

### 7.1 迭代目标

用户能够快速新增一笔记录，并按账本、时间和分类查看与维护记录。

### 7.2 功能需求

#### R3-01 快速记账

- 必填：金额、分类、账本、记录时间、币种、支付方式。
- 可选：备注。
- 金额必须大于 0，输入和计算使用十进制。
- 默认选择上次使用的账本、币种和支付方式。
- 提交期间禁用重复提交。
- 成功后显示记录 ID，并允许“再记一笔”或“查看详情”。

#### R3-02 记账列表

- 必须按 `accountBookId` 查询。
- 支持分页、开始/结束时间和分类筛选。
- 每项展示金额、分类、时间、币种、支付方式和备注摘要。
- 收入、支出使用可访问性友好的视觉差异，不能只依赖颜色。

#### R3-03 记账详情

- 使用记录 ID 和 accountBookId 获取详情。
- 展示完整字段。
- 根据账本权限显示编辑和删除入口。

#### R3-04 编辑与删除

- 编辑 body 必须携带 `id` 和 `accountBookId`。
- body `id` 与 path `id` 必须相同。
- 删除需要同时发送 path `id` 和 query `accountBookId`。
- 删除成功后返回列表并移除对应项。

#### R3-05 时间范围查询

- 支持通过 `GET /api/accountings/by-time-range` 获取跨账本时间范围记录。
- DateTime 必须携带明确时区或按统一约定格式发送。

### 7.3 接口范围

- `POST /api/accountings`
- `GET /api/accountings`
- `GET /api/accountings/{id}`
- `PUT /api/accountings/{id}`
- `DELETE /api/accountings/{id}`
- `GET /api/accountings/by-time-range`

### 7.4 验收标准

- 从主页进入后，常用数据已存在时可在 3 个主要操作步骤内完成记账。
- 新增成功后列表和账本金额正确刷新。
- 筛选、分页、编辑、删除均通过真实网关联调。
- 时区切换或跨日数据不会错误显示到相邻日期。
- 金额展示精度一致，不出现浮点误差。

## 8. Iteration 4：预算与报表

### 8.1 迭代目标

用户能够制定预算、查看执行情况并获取基础财务报表。

### 8.2 功能需求

#### R4-01 预算列表与详情

- 支持按年、月分页查询预算。
- 支持查看当前有效预算。
- 展示预算金额、剩余金额、分类、周期和起止时间。
- 预算超支、即将耗尽和正常状态应有明确文案。

#### R4-02 预算创建与维护

- 支持年、月、季度三种周期。
- 校验结束时间不早于开始时间。
- 编辑 body ID 与 path ID 必须一致。
- 删除前二次确认。

#### R4-03 预算消耗记录

- 获取预算 ID 到记录数组的 Map。
- 按预算分组显示使用金额和日期。
- 正数表示消耗，负数表示回补。

#### R4-04 预算进度与趋势

- 展示预算总额、已使用、剩余和报告日期。
- 使用折线图或柱状图展示消耗趋势。
- 无数据时显示解释性空状态。

#### R4-05 基础报表

- 支持月报、季报和年报。
- 展示年份、月份和金额。
- 图表必须提供文本摘要，保证无障碍可读性。

### 8.3 接口范围

- `/api/budgets...`
- `GET /api/budget-records/by-budget-ids`
- `GET /api/budget-reports/budget-progress`
- `GET /api/budget-reports/budget-consumption-trend`
- `POST /api/Report/GetReport`

### 8.4 验收标准

- 可完成预算 CRUD。
- 预算剩余值、消耗记录和图表数据一致。
- 月、季、年报均能正确切换。
- HTTP 200 + 空数组不会被展示为错误。
- 图表在深色模式、字体放大和横竖屏切换后仍可读。

### 8.5 已知限制

AI 预算生成尚未实现；预算智能解读和通用报表智能解读尚未发布到网关，本迭代不展示相关入口。

## 9. Iteration 5：文件、OCR 与智能录入

### 9.1 迭代目标

降低记账录入成本，使用户可通过图片或自然语言生成记账草稿。

### 9.2 前置条件

- 后端将 `PresignedURLResponse` 的公共字段改为可序列化属性，或显式开启字段序列化。
- 确认 OSS 预签名 URL 的 Content-Type、有效期和 PUT 请求头要求。
- 客户端获得相机/相册所需权限，并遵循 Android Photo Picker 优先原则。

### 9.3 功能需求

#### R5-01 文件上传

- 支持服务端 multipart 上传作为兜底路径。
- 支持预签名直传作为推荐路径。
- 上传前检查文件大小、MIME 类型和扩展名。
- 展示上传进度、取消、失败重试。
- 向 OSS PUT 时不得携带 Gateway Bearer Token。

#### R5-02 OCR

- 用户选择或拍摄票据后上传文件。
- 调用识别接口并展示处理中状态。
- 识别完成后获取文本。
- 允许用户复制、编辑识别文本并用于记账草稿。

#### R5-03 文本金额与分类提取

- 用户输入自然语言，例如“午餐花了 28 元”。
- 请求 body 使用 JSON 原始字符串，不封装为 `{text: ...}`。
- 将返回的金额、币种和分类填入草稿。
- 所有 AI/规则提取结果必须由用户确认后才能创建记账记录。

#### R5-04 分类预测

- 将文本、候选分类、商户、金额桶和小时信息发送预测接口。
- 展示预测分类和置信度。
- `requiresUserConfirmation=true` 时必须要求用户选择。
- 用户采用预测时发送 choice 反馈；用户纠正时发送 correction 反馈。
- 客户端不向普通用户展示 retrain 操作。

### 9.4 接口范围

- `/api/files...`
- `/api/ocr/recognize`
- `/api/ocr/text`
- `/api/assistant/extract-amount-and-category`
- `/api/CategoryPrediction...`

### 9.5 验收标准

- 支持从图片到记账草稿的完整流程。
- 上传失败可重试且不会重复确认文件。
- AI 结果不会未经确认直接入账。
- 相机权限拒绝后仍可使用系统文件选择器。
- 预签名 URL、OCR 原文和票据图片遵循隐私与缓存清理策略。

## 10. Iteration 6：协作与财务健康

### 10.1 迭代目标

支持账本分享、多人费用分摊和财务健康分析。

### 10.2 功能需求

#### R6-01 账本分享

- 分享给一个或多个用户。
- 设置只读、读写或管理权限。
- 查看“我分享的”和“分享给我的”分页列表。
- 支持修改权限与撤销分享。
- 当前新增请求字段名为 `userId` 但类型为数组，DTO 必须严格匹配。

#### R6-02 分摊项目

- 创建分摊项目，选择账本、总金额、币种、分类、日期和参与者。
- 支持按比例、人均、固定金额、混合四种方式。
- 提交前校验参与者金额合计与总金额的关系。
- 支持列表、详情、编辑和删除。

#### R6-03 提醒

- 为参与者创建未支付、逾期或手动提醒。
- 查看某分摊项目的提醒列表。
- 更新提醒状态；body ID 必须与 path ID 一致。

#### R6-04 结算

- 创建结算记录，包含付款人、收款人、金额、支付方式、日期、凭证和备注。
- 查看单条结算与项目下全部结算。
- 结算完成后刷新参与者支付状态。

#### R6-05 财务健康

- 选择账本和统计周期计算健康评分。
- 展示总评分、各维度得分、健康等级和统计周期。
- 展示历史分页列表。
- 获取单账本改善建议。
- 尚无最新评分时展示引导计算的空状态。

### 10.3 接口范围

- `/api/account-books/share...`
- `/api/shared-expenses...`
- `/api/shared-expense-reminders...`
- `/api/shared-expense-settlements...`
- `/api/financial-health...`

### 10.4 验收标准

- 能完成分享、权限修改和撤销流程。
- 四种分摊方式都有校验测试。
- 结算后金额与参与者状态正确。
- 财务评分和建议在无数据、部分数据、完整数据下均正确展示。
- 无权限操作时 UI 与服务端 403 行为一致。

## 11. Iteration 7：通知与账号闭环

### 11.1 迭代目标

补齐站内通知和移动端账号生命周期，使应用可以独立完成注册、绑定、重置和退出。

### 11.2 后端前置条件

以下控制器路径必须加入 Gateway，并正确配置匿名路径：

- `POST /api/auth/register`
- `POST /api/auth/emailVerificationCode`
- `POST /api/auth/smsVerificationCode`
- `POST /api/auth/email/bind`
- `POST /api/auth/phone/bind`
- `PUT /api/auth/password/reset`
- `POST /api/auth/logout`
- `GET /api/auth/userinfo`（如客户端资料需要）

### 11.3 功能需求

#### R7-01 站内通知

- 展示通知分页列表、未读数和详情。
- 支持标记已读和批量删除。
- App 前台时刷新未读数。
- 群发、编辑能力仅对有管理权限的用户显示。

#### R7-02 注册

- 支持用户名、密码、邮箱或手机号、验证码注册。
- 明确验证码发送类型和注册时 email/phone 的组合规则。
- 注册成功后返回用户 ID，并引导登录。

#### R7-03 邮箱与手机号绑定

- 发送验证码后显示倒计时。
- 限制重复发送。
- 绑定成功后刷新验证状态。

#### R7-04 重置密码

- 支持按邮箱或手机号重置。
- 校验新密码规则与确认密码一致。
- 重置成功后清除旧会话并返回登录页。

#### R7-05 退出登录

- 调用后端 logout 撤销服务端 Token。
- 无论服务端是否可达，用户确认退出后都应安全清理本地会话；若撤销失败需记录可诊断状态。

### 11.4 验收标准

- 新用户能从注册完成到首次登录。
- 用户能绑定邮箱/手机号并重置密码。
- 登出后旧 access token 无法继续调用受保护接口。
- 通知未读数、列表和已读状态保持一致。
- 验证码倒计时在页面旋转和进程恢复后不会异常重置。

## 12. Iteration 8：增强、修复与正式发布

### 12.1 迭代目标

在后端阻塞项解决后补齐增强能力，并达到正式发布质量。

### 12.2 功能需求

#### R8-01 周期性支出

后端必须先完成：

- 将删除接口改为唯一方法与路径，建议 `DELETE /api/recurring-expense-rule`。
- 将单条查询改为 `GET /api/recurring-expense-rule/{id}`。
- 将分页改为 `/api/recurring-expense-rule/page`。
- 同步更新 Gateway。

修复后客户端实现规则新增、编辑、删除、详情和分页列表；频率包括天、周、月、季度、年。

#### R8-02 报表智能解读

- 后端发布 `budget-insight` 和 `GetReportInsight` 网关路由。
- 展示概要、健康等级、指标、亮点、风险和建议。
- 明确标识内容由规则还是 LLM 生成。
- 对 LLM 内容提供免责声明和刷新策略。

#### R8-03 AI 预算生成

- 仅在后端实现并明确确认流程后开发。
- AI 生成预算必须先展示草稿，由用户确认后保存。
- 禁止自动覆盖已有预算。

#### R8-04 性能与稳定性

- 优化冷启动、首屏加载和列表滚动。
- 为关键列表增加合理缓存。
- 验证弱网、断网、超时、后台恢复和进程重建。
- 完成崩溃监控与性能监控接入，敏感数据脱敏。

#### R8-05 发布准备

- 完成应用图标、启动页、隐私政策、用户协议和版本说明。
- 完成权限用途说明和数据安全表单。
- 生成签名的 Release 包并执行回归测试。
- 执行 Play Console 或目标应用商店的兼容性检查。

### 12.3 验收标准

- 所有 P0/P1 缺陷关闭。
- 核心流程崩溃率、ANR、接口失败率达到团队发布阈值。
- Release 构建关闭敏感网络日志。
- 隐私政策覆盖账号、财务、票据图片、OCR、AI 和日志数据。
- 完成至少一轮真实设备回归测试。

## 14. 数据与缓存要求

### 14.1 必须持久化

- access token、refresh token、过期时间。
- 当前环境标识（仅调试构建允许切换）。
- 最后选择的账本 ID。
- 用户偏好设置。

### 14.2 可缓存

- 账本列表。
- 分类、币种、支付方式。
- 最近一次成功获取的预算与报表数据。

### 14.3 禁止长期明文保存

- 密码、短信或邮箱验证码。
- OAuth 客户端密钥。
- 完整请求/响应日志中的 Token。
- 预签名上传 URL。
- 用户未确认保存的敏感 OCR 文本和票据图片。

### 14.4 缓存一致性

- 写操作成功后更新或失效对应缓存。
- 切换账号时清空所有用户级缓存。
- 切换账本时取消旧账本未完成请求，避免数据串页。
- 缓存数据需标注更新时间，并允许用户手动刷新。

## 15. 非功能性需求

### 15.1 性能

- 常规页面交互保持流畅，列表避免主线程执行网络、数据库和大图解码。
- 首屏只请求必要数据，非核心模块延迟加载。
- 图片上传前按业务允许范围压缩，保留必要清晰度。

### 15.2 可访问性

- 所有可点击图标提供语义描述。
- 支持系统字体缩放。
- 收入/支出、正常/风险状态不能只依赖颜色区分。
- 重要图表提供文字摘要。
- 点击区域满足 Material 最小触控尺寸。

### 15.3 安全与隐私

- 正式环境启用 HTTPS，禁止信任所有证书。
- Release 构建关闭 body 级网络日志。
- Token 不写入普通日志或崩溃自定义字段。
- 账号退出和切换时清理用户级缓存。
- 文件与 OCR 数据遵循最小保存原则。
- 不向第三方分析平台上传金额、账目内容、OCR 原文和身份凭据。

### 15.4 可维护性

- 网络 DTO、领域模型和 UI 模型按需要分离。
- 不在 UI 层直接处理 Retrofit Response。
- 枚举、日期、金额和错误映射集中实现。
- 每个 feature 提供清晰的状态、事件和副作用边界。

### 16.3 UI 测试

- 登录成功与失败。
- 首次无账本引导。

## 18. 需求优先级

- P0：工程基线、登录、会话、账本、基础资料、记账 CRUD、错误处理。
- P1：预算、基础报表、文件/OCR、账本分享、分摊、财务健康、通知。
- P2：分类预测反馈、智能解读、AI 预算生成、周期性支出、管理端能力。

若后端依赖未满足，不允许通过直连微服务或在客户端硬编码临时密钥规避。

## 19. Definition of Ready

一个需求进入迭代开发前必须满足：

- 产品目标和用户场景明确。
- API 已在 Gateway 发布并可在测试环境调用。
- 请求、响应、枚举、空值、错误码已确认。
- UI 设计或交互说明可用。
- 权限、隐私和埋点要求已明确。
- 后端阻塞项已关闭或存在不影响交付的降级方案。

## 20. Definition of Done

一个需求完成必须满足：

- 功能和异常路径均已实现。
- 单元测试与必要 UI 测试通过。
- 真实 Gateway 联调通过，不使用 Mock 作为最终验收依据。
- Loading、Empty、Error、Content 状态完整。
- 深色模式、字体缩放和基础无障碍检查通过。
- 无敏感日志、明文密码或硬编码密钥。
- 文档、DTO 和接口变更同步更新。
- 产品验收通过且无未说明的 P0/P1 缺陷。

## 21. 首个可发布版本建议

首个内部测试版本包含 Iteration 0～3：密码登录、账本、分类、币种、支付方式和完整记账闭环。

首个公开 MVP 建议包含 Iteration 0～4，并在后端补齐注册、重置和退出能力后吸收 Iteration 7 的账号闭环部分。文件/OCR、协作和智能能力可作为后续版本逐步开放，不应阻塞基础记账产品发布。
